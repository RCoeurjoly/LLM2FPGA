* Task 6 M2.1-M2.4 Dataflow

This is the working, evidence-based view of the M2 path. It describes what the
board must prove through public PCIe/BAR behavior before we count a
submilestone.

** Acceptance rule

- HIL evidence must use direct host writes and strict readback. Compensated
  host writes, private RTL probes, clear-only runs, and debug-only PASS states
  are diagnostics.
- If a board gate fails, reproduce the same public-interface failure in
  simulation. If simulation passes and HIL fails, the simulation is not faithful
  enough to the implemented hardware boundary. Extend the sim or add a narrower
  diagnostic; do not treat the mismatch as milestone progress.
- A submilestone is complete only when its named boundary has an offline oracle,
  a self-checking sim, a timing-clean bitstream, PCIe recovery to =pcie_ready=,
  and a strict board artifact.

** M2.1 PCIe/BAR contract

The contract is simple: direct host writes to M2 input, residual, and control
must read back identity through the same public BAR interface. The host must not
apply lane-order compensation.

** M2.2 start/clear lifecycle

The lifecycle contract proves that the public control/status path is stable:
=start_count= increments on start, DONE/ERROR is decoded, clear returns to
IDLE, and the BAR does not become stale or all ones.

Current status:

- M2.2 is HIL-green for the earlier focused M2 candidate recorded in
  =artifacts/task6/runs/task6-bottleneck/m2-2-start-clear-lifecycle-candidate.json=.
- M2.2 must be rerun on any new M2.4 bitstream before accepting later compute
  evidence, because timing or reconfiguration changes can perturb the hardware
  boundary.
